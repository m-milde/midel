## 3. Why the current size cannot hold the library (capacity reasoning)

*Estimate — uncertain; the trial in Section 9 is the real answer.*

- A rule of thumb from published language-model research is that a transformer can memorize on the order of **~2 bits of knowledge per parameter**.
- The library holds ≈ 445k tokens in the lesson files (plus ≈ 200k more if the 17,972 short lines are included, Section 5.10, so ≈ 650k in total). Even at a generous few bits per token that is **several million bits**, which needs **millions of block parameters at the very least**, and in practice **5–10× more** because training is imperfect (multiple epochs, interference between lessons).
- The current blocks have **0.53M** parameters. That is an order of magnitude too small, which matches the observed **~8% recall**.
- Conclusion: a rebuild should target roughly **6–25M total parameters**, with most of the growth in the blocks, not in the word table.

## 4. Target specification

### 4.1 Recommended architecture changes

| Setting | Today | Recommended | Reason |
|---------|-------|-------------|--------|
| Context (`MAX_LEN`) | 128 | **256** | All current lessons fit 192. Planned practical answers (checklists, steps, formulas) will exceed 128. Attention cost at 256 is small for this size. |
| Feed-forward width | 2×d | **4×d** | Facts are mostly stored in the feed-forward layers; 4× is the standard choice. |
| Input/output embeddings | separate | **tied** (one shared table) | Saves V×d parameters (≈5M at V=21k, d=256) and usually helps rare words. |
| Weights in the browser | Float64 | **Float32** (from fp16 or int8 file) | Halves memory; see 5.2–5.3. |
| Tokenizer | word-level, drops symbols | **v2: see 5.9** | Controls vocabulary size. |

### 4.2 Size tiers to try (parameter counts are calculated; V = 21,244 tied)

Per block ≈ 12·d² parameters (attention 4d² + feed-forward 8d²).

| Tier | Layers × width × heads | Blocks | Embedding (tied) | **Total** | File fp16 | File int8 |
|------|-----------------------|--------|------------------|-----------|-----------|-----------|
| **S** | 6 × 192 × 6 | 2.65M | 4.07M | **≈ 6.8M** | ≈ 14 MB | ≈ 7 MB |
| **M (start here)** | 8 × 256 × 8 | 6.29M | 5.43M | **≈ 11.8M** | ≈ 24 MB | ≈ 12 MB |
| **L** | 10 × 384 × 12 | 17.7M | 8.14M | **≈ 26M** | ≈ 52 MB | ≈ 26 MB |

(If the tokenizer shrinks the vocabulary to ~12k, subtract ≈ 40% of the embedding column.) Untied embeddings add V×d parameters.

**Rule:** train **S, M and L trials**, ship the **smallest tier that passes Section 7**. Record train time, file size, load time and phone latency for each (template in Section 9).

**Deploy budget (default accepted 21 Oct 2026):** the brain file should be **≤ 30 MB (soft target)** and **never above 60 MB (hard limit)**. That allows tier M in fp16 or tier L in int8. Two things make the size less critical than it sounds:
1. **The browser caches the file** (the `?v=` cache-bust changes only when the brain changes), so size mostly affects the **first visit**.
2. **The brain loads in the background** (Section 5.3): the page opens and answers from the library as soon as the library files are in; the deep network switches on when its file arrives.

### 4.3 How long may a stored answer be? (authors and Cursor)

**The library has no length limit** — it always shows the full stored text. The limit comes from the **network's context window**: question + answer together must fit. Today that is **128 tokens**; the rebuild moves it to **256** (4.1).

A *token* is a word or a punctuation mark. Measured on the library (21 Oct 2026): **about 1.14 tokens per word**, and the question takes about 8–10 tokens.

Measured length of today's lessons (question + answer, in tokens):

| Sentences in the answer | Lessons | Median tokens | Longest |
|-------------------------|---------|---------------|---------|
| 1 | 1,564 | 28 | 84 |
| 2 | 6,258 | 43 | 159 |
| 3 | 1,355 | 60 | 88 |
| 4 | 645 | 41 | 131 |
| 5 | 50 | 75 | 102 |
| 6–9 | 13 | 73–98 | 136 |

The practical, rewritten survival answers (checklists with numbers) have a median of **83 tokens (about 67 words)** and a longest of 114.

| Answer length | Words (answer) | Tokens (question + answer) | Status |
|---------------|----------------|----------------------------|--------|
| **Standard (recommended)** | up to ~110 | ≤ ~128 | Fits today's network and the rebuilt one; best recall. **4–8 sentences** is fine. |
| **Long (allowed after the rebuild)** | ~110–170 | ~128–200 | Needs the 256 context, so it works only in the rebuilt network. Fine for the library today. Expect slightly lower recall and slower generation. |
| **Too long for training** | > ~170 | > ~200 | Do not write it as one lesson. Split it into two lessons (for example "How do I purify water?" and "How do I purify water: details?"), or accept that only the first part is trained and the library carries the rest. |

Cost of length, so authors can decide: every extra token must be **memorized** (capacity), is a place where generation can **go wrong**, and costs **time** — at the 50 ms/token budget (5.3), 100 tokens ≈ 5 s and 200 tokens ≈ 10 s of generation. The library answer appears instantly regardless.

Notes for the normalization step (5.4): each bullet or line break becomes a sentence boundary (+1 token), and math symbols become words (`×` → "times"), so **formula-heavy or list-heavy answers grow by roughly 10–20%** in the training copy. Re-check the longest lessons with `npm run corpus:stats` after normalization is defined.

## 5. Gaps and how to close them

### 5.1 Training framework (G1) — **approved by the owner (21 Oct 2026, "no restrictions")**

- **Estimate of training cost.** Compute ≈ 6 × parameters × training tokens. With M (~12M params), ~5 paraphrase variants per lesson (check `prompt_variants()`), ~45 tokens each, 60 epochs: about 9.9k × 5 × 45 × 60 ≈ 133M tokens → **≈ 1×10¹⁶ operations**.
  - NumPy float64 on the M3 CPU (≈ 20–50 GFLOP/s effective): **≈ 2–6 days**.
  - PyTorch on the M3 GPU (MPS) or one rented GPU (≈ 0.5–2 TFLOP/s effective): **≈ 2–6 hours**.
  - These are rough; measure with a 100-step benchmark first.
- **Decision:** write the new trainer in **PyTorch** (free software; trains on the Mac's graphics chip through "MPS", or on an NVIDIA GPU through CUDA). Keep `train_stage3.py` and the NumPy `.venv` untouched as the readable teaching trainer; install PyTorch in a **separate virtual environment** (for example `.venv-torch`). **Export to the format in 5.2** so `deep_model.js` stays the single inference path.
- This **replaces** the old hard rule "Interpreter: `.venv/bin/python` (NumPy). No GPU path" in CURSOR_DEEP_NETWORK_FIXES.md §2 for the rebuild.
- **Renting a GPU** is allowed **only if** the benchmark (runbook step 8) shows the Mac is too slow. Before renting, Cursor tells the owner the expected cost and run time, because it spends money.

### 5.2 Weight file format v2 (G2)

Today: decimal text in a `.js` file, 9.5 bytes per weight.

Proposed:
1. **`stage3_brain.bin`**: fp16 or int8 weights (int8 with a per-row scale), little-endian, one flat buffer.
2. **`stage3_brain.json`** (or a small `.js`): config (layers, width, heads, context, vocab size, tied flag, dtype), the vocabulary/merge table, scales, and a **format version**.
3. `deep_model.js` loads via `fetch` + `ArrayBuffer`, **streams progress** to the loading screen, then converts to **Float32Array** once.
4. Keep a `version` field; `deep_model.js` must refuse an unknown version with a clear message and keep the library working.
5. **Protection:** extend the hotlink-protection rule and the `X-Robots-Tag` header in `.htaccess` (both currently match `\.(js|json)$`) to the new `.bin` file, and add `.bin` to `scripts/test-htaccess.mjs`. The network file is as downloadable as the lessons (MODEL.md "Protecting the lesson files").
6. `pack_midel_backup.py` already sums script sizes for the loading-screen progress bar; extend it to count the `.bin` as well and to exclude `*.trial.*` / `*.joint.*` files.

### 5.3 Browser inference budget (G3)

**Reference device (owner: "the regular form factor", 21 Oct 2026):** a **typical mid-range phone** — roughly 4 GB RAM, bought in the last ~4 years — on normal 4G or Wi-Fi. If no such phone is at hand, Cursor emulates it in Chrome DevTools / Playwright with **CPU throttling ×4** and a **"Fast 4G"** network profile (the loading-screen tests already use throttled connections), and repeats the key numbers on a real phone when possible.

**Background loading (default, replaces "load everything behind the loading screen" once the brain is large):**
1. The loading screen waits only for the **library** (facts, matcher, page code) — about 3–4 MB today.
2. The brain (`stage3_brain.bin` + header) then **streams in the background** after the home page is shown; a small quiet indicator is enough. Until it arrives the page answers from the library exactly as today.
3. Decoding and preparing the weights happens in the **Web Worker**, never on the main thread, so the background animation and typing stay smooth (the 2-second freeze we removed on 20 Oct must not return).
4. If the brain fails to load, nothing breaks: library-only mode.


- Weights in memory as **Float32** (M at fp32 ≈ 47 MB RAM; Float64 would be ≈ 94 MB — too much for a low-end phone).
- Keep the existing **K/V cache** generation. Add a **latency budget**: measure milliseconds per generated token on a mid-range phone; target **≤ 50 ms/token** for the chosen tier *(proposed)*. Cost per token is roughly 2 × parameters operations (*estimate*: ~24 MFLOP for M).
- Run generation in a **Web Worker** so the UI, the background animation and the loading transition never block.
- If a tier is too slow in plain JavaScript, options in order: smaller tier → int8 matmul → WebAssembly SIMD → WebGPU. Decide by measurement.
- The page must keep working with **library-only answers** if the brain fails to load or is too slow.

### 5.4 Training-text normalization (G4) — new since 13 Oct

Library answers are now stored with structure, for example (survival):

```
Early signs are shivering, numb hands and feet, and clumsiness.
**Dangerous signs**
- Confusion, slurred speech, drowsiness, or shivering that suddenly stops.
**What to do**
- Get out of wind and wet; ...
```

and with math symbols: `x = (−b ± √(b² − 4ac)) / (2a)`.

The current tokenizer keeps only lowercase words, numbers and `? . ! ,`. So bullets/bold/newlines vanish and `× ÷ ² ± √ − %` disappear.

**Requirement:** define one function, `training_text(answer)`, used by the trainer **and** the page, that:
1. Removes `**`, heading and bullet markers, and turns each line break or bullet into a sentence boundary (so a list becomes consecutive sentences).
2. Maps symbols to tokens (proposed): `×`→"times", `÷` and `/` between numbers→"divided by", `²`→"squared", `³`→"cubed", `±`→"plus or minus", `√`→"square root of", `−`→"minus", `%`→"percent", `π`→"pi", `≤ ≥`→"at most" / "at least". Extend as needed; keep a table in the code.
3. Is **reversible enough** for display: network output is plain sentences; the page's `answer_format.js` already turns sentences into paragraphs/bullets, so network answers get the same layout as library answers.

The **library stays the source of truth** and shows the stored (structured) text; only the **training copy** is normalized. Re-run `npm run corpus:stats` on the normalized corpus.

### 5.5 Corpus freeze and manifest (G5)

The library grows daily (survival rewrites, new packs, Wikipedia batches). For every training run:
1. Stop wiki batches and writers (`save_taught.py` stays idle) or work on a **frozen copy**.
2. Write `versions/corpus-manifest-YYYY-MM-DD.json`: list of fact files, row counts, a **hash per file**, tokenizer version, normalization version, total teachable rows.
3. Train **only** from that frozen snapshot. Store the manifest next to the exported brain.
4. A brain without a manifest is not eligible to replace the live brain.

**Content policy (owner decision):** the library includes categories such as *Swear Words*, *Weed* and *Controlled Substances*. Decide whether they are **trained into the public network** or stay **library-only** (the field hop already excludes them). Default proposal: **library-only**.

### 5.6 Learning without forgetting (G6) — the release-cycle model

Per-lesson installs (`--learn-new`) are what caused the forgetting, and a bigger network trained one lesson at a time would do the same. The rule after the rebuild:

1. **The library is always current.** New lessons are answered from the library immediately (this already works and needs no training).
2. **The network is rebuilt in releases ("consolidation"), not patched per lesson.** Each release trains on the **entire** frozen corpus: **every epoch sees every lesson** (full rehearsal = the standard cure for forgetting), shuffled each epoch.
3. **When to cut a release** (proposed): when new or changed lessons reach **~5% of the corpus**, or monthly, whichever comes first; always after a big pack or rewrite batch.
4. A release **warm-starts from the previous weights** when the architecture and tokenizer are unchanged (cheaper), and otherwise trains from scratch.
5. **Accept a release only if** the evaluation floor holds on **old and new** lessons (Section 7); otherwise keep the previous brain. This is the guard against silent forgetting.
6. Retire `learn:new:loop` for the large network. If a light between-release update is ever wanted, use **adapters (LoRA-style)** on top of a frozen base — a separate, later project, **not** part of the rebuild.
7. Optional, later: extra rehearsal weight on categories that score low in the per-field eval.

### 5.9 Tokenizer v2 (G9)

Facts: 21,244 distinct words, 33% seen once. With a word table, the embedding grows with every new word and rare words are never learned.

Options:
1. **Keep word-level** (+ the symbol mapping in 5.4). Simple, but ~21k+ vocabulary and growing.
2. **Subword (BPE/Unigram), ~8–16k tokens** *(recommended)*: rare words become pieces of known words, vocabulary stays bounded, new lessons rarely add tokens, acronyms and numbers behave consistently.

**Simplification:** the network tokenizer only needs to be shared by **`train`** and **`deep_model.js`**. The library matcher (`science_library.js`) keeps its own word logic; it does **not** need the subword rules (this relaxes the earlier "three places" requirement in ROADMAP Phase C).

Acceptance: exact encode/decode round trip on all lessons; the same output from the Python trainer and the JavaScript page on a fixed test file; vocabulary ≤ 16k; the merge table fits in the small header file.

**Inventory check (build before the first run; runbook step 4):** a read-only script, for example `npm run corpus:inventory`, that prints one line per source — files found, rows read, rows trainable, rows excluded **with the reason** (no question, restricted category, unparsable) — and fails if the totals do not add up to the frozen manifest. Its output is saved in the corpus manifest. A brain is not accepted if the inventory is missing.

**After the rebuild:** lessons added later (Wikipedia batches, Remember, manual edits, new packs) are **answered by the library at once** and enter the network at the **next release** (5.6). The network never needs to know a lesson in order for the user to get its answer.

## 8. Chat behavior after the rebuild

Unchanged principle: **the library is the source of truth**, the network is the writer/continuer.
- Default: show the stored library answer (structured, formatted).
- Follow-ups reuse the last topic (`chat_context.js`): lookup is rewritten, previous tokens are prefixed for generation.
- Network-composed text only when a **per-prompt** generation check passes (CURSOR guide Steps 8–11), with the library answer as fallback.
- Calculator, suggestions, formatter and loading screen behave as in 5.8.
